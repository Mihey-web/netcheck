# Сервисо-центричная выдача, свой сайт и замер замедления

Дата: 2026-08-07. Статус: утверждено владельцем (вариант «выдача + замедление», замер — по кнопке).

## Цель

Приложение должно прямо отвечать на вопрос пользователя: **какие сервисы в этой
сети работают, какие нет, и почему** — списком статусов по-русски, а не абзацем
текста и технической таблицей. Плюс проверка произвольного сайта с главного
экрана и честный ответ про замедление (YouTube «работает», но задушен — сейчас
приложение про это молчит).

## 1. Статусы сервисов (бэкенд)

`verdict.ServiceVerdict` дополняется двумя полями-кодами (вычисляются в
`verdict.Build` из уже собранных фактов, фронт логику НЕ дублирует):

> Изменено 2026-08-07 по итогам живого теста владельца: статус обязан отвечать
> на практический вопрос «откроется ли сайт у меня в браузере ПРЯМО СЕЙЧАС»,
> а не на абстрактный «блокируют ли его». С включённым VPN (системный прокси →
> живой листенер) YouTube работал, а оранжевое «только через VPN» читалось как
> «не работает». Прежний `vpn_only` расщеплён на `ok_via_vpn`/`need_vpn` по
> признаку `vpnCoversBrowser`.

В `verdict.Build` вводится признак **vpnCoversBrowser** — «VPN применяется к
трафику браузера сейчас»: DefaultViaTunnel (TUN — весь трафик в туннеле) ИЛИ
системный прокси Windows включён и указывает на активный прокси-листенер
(если листенеров не нащупали вовсе, включённому прокси верим). Флаг отдаётся
фронту как `Verdict.VPNCoversBrowser` (`json:"vpnCoversBrowser"`) — для строки
контекста «VPN применяется к браузеру» / «браузер идёт мимо VPN».

- `Status string` (`json:"status"`) — одно из:
  - `ok` — работает напрямую;
  - `ok_via_vpn` — напрямую заблокирован, но через VPN открылся (замер!) И
    vpnCoversBrowser → «сейчас работает (через ваш VPN)»; зелёный,
    не тревожный. Геоблок с удачным замером через VPN сюда же: выход VPN
    оказался в подходящей стране;
  - `need_vpn` (бывший `vpn_only`) — заблокирован, через VPN открывается
    (или замера не было), но VPN сейчас браузер НЕ покрывает (Cause =
    dpi_sni/ip_block/http_drop/dns_spoof/isp_stub/stateful…);
  - `geo` — сам сайт не пускает из РФ (Cause = geo_block); при неудачном
    контрольном замере через VPN остаётся geo (не need_vpn и не down),
    advice — «нужен VPN с выходом в другой стране»;
  - `challenge` — антибот/капча, в браузере скорее всего откроется
    (Challenged или Cause = antibot);
  - `down` — не работает нигде (Cause = service_down, или заблокирован и через
    VPN тоже не открылся / ProxyTried && !ProxyOK при блокировке; во втором
    случае advice — `advice.vpn_fail`: «не открылось ни напрямую, ни через
    VPN», а не «сервис лежит у всех»);
  - `unknown` — не удалось определить (Cause = unknown/пусто при провале).
- `Advice string` (`json:"advice"`) — код совета «что делать»:
  - `advice.vpn` (заблокировано провайдером → поможет VPN/обход DPI),
  - `advice.vpn_keep` (ok_via_vpn: работает через ваш VPN — не выключайте),
  - `advice.vpn_fail` (не открылось ни напрямую, ни через VPN — дело в
    VPN-сервере, попробуйте другой сервер/страну выхода),
  - `advice.geo` (нужен VPN с выходом НЕ в РФ),
  - `advice.browser` (капча — просто откройте в браузере),
  - `advice.dns` (DNS-подмена → включите DoH/смените DNS, если Cause=dns_spoof;
    остаётся и при down: смена резолвера работает без VPN),
  - `advice.wait` (сервис лежит сам — остаётся ждать),
  - `advice.none` (работает / сказать нечего).

Таблица соответствия Cause→(Status, Advice) — единственное место истины,
рядом с ней табличный тест на каждый Cause (плюс пары «тот же Cause при
vpnCoversBrowser=true/false → ok_via_vpn/need_vpn»). Существующие поля
не трогаются, Relocalize не затрагивается (коды языконезависимы).

## 2. Выдача на главном экране (фронтенд)

- Главный блок после прогона — список сервисов из `report.verdict.services`
  (плюс работающие: сейчас в services только проблемные — Build дополняется
  записями со `status:"ok"` для успешных целей групп blocked/geo, чтобы список
  был полным ответом, а не списком жалоб).
- Строка: значок статуса + имя сервиса + короткая строка статуса. Клик
  раскрывает: причина (уже локализованный Reason из вердикта), совет
  «что делать» (по коду Advice из i18n), кнопка «замерить скорость» (см. §4)
  где применимо.
- Порядок: сломанные сверху (down, need_vpn, geo, challenge, unknown,
  ok_via_vpn, ok). Рядом с списком — строка контекста по
  `verdict.vpnCoversBrowser`: «VPN включён и применяется к браузеру» /
  «VPN запущен, но браузер идёт мимо него» (вторая не дублирует
  warn.proxy_bypass из Lines — это короткий статус, а не предупреждение).
- Сводный вердикт (первая строка текущего Lines) остаётся заголовком блока.
- Текущая таблица проб и tally уезжают под раскрывашку «Технические детали»
  (закрыта по умолчанию, состояние запоминается в конфиге UI).
- История: старые отчёты без `status` рендерятся как сейчас (фолбэк по
  наличию поля).

## 3. Свой сайт с главного экрана

- Поле ввода + кнопка «Проверить» рядом с главной кнопкой (та же валидация
  hostOk, что во вкладке «Сервисы»).
- Новый биндинг `RunSingle(host string) runner.Report`: прогон базовых слоёв
  (gateway/dns/runet-минимум — только эталон) + одна цель host в группе
  blocked. Использует тот же busy-флаг, что RunCheck (второй прогон
  параллельно не стартует, событие run-busy). Прогресс — те же события.
  В историю single-прогон НЕ пишется (это точечный вопрос, не срез сети).
- Результат — карточка сервиса (как в §2) над списком; кнопка «добавить в мой
  список» → существующий механизм custom-целей.

## 4. Замер замедления (по кнопке)

- `internal/probe/speed.go`: `MeasureSpeed(ctx, url, viaProxy)` — качает до
  5 МБ или до 8 с (что раньше), считает Мбит/с; уважает ctx; первые 256 КБ
  отбрасываются из расчёта (TCP slow start / burst до шейпера).
- Каталог: поле `SpeedURL` у сервиса. Волна 1:
  - эталон — `https://speed.cloudflare.com/__down?bytes=5242880` (отдельная
    константа, не сервис);
  - YouTube — прямая ссылка сегмента через Innertube API (ANDROID-клиент,
    публичный ключ, unsigned URL из streamingData). Если получить не удалось —
    честное «не удалось замерить» (не «не замедлен»!). Реализация в
    `internal/probe/ytspeed.go`, помечена как best-effort.
- Биндинг `MeasureSpeed(serviceID string) SpeedResult`:
  `{ServiceMbps, RefMbps, ProxyServiceMbps (если есть прокси), Status, Err}`.
  Пороги: ServiceMbps < 0.25×RefMbps И ServiceMbps < 2 Мбит/с → `slow`;
  0.25–0.5×эталона → `maybe_slow` («похоже на замедление, не уверен»);
  иначе `normal`. Через VPN быстрее ×4+ — усиливает вердикт slow.
- UI: кнопка в раскрытой строке сервиса (у кого есть SpeedURL) и результат
  в строке: «🐢 замедлен в ~N раз (0.4 Мбит/с, через VPN — 80)». Результат
  живёт в сессии; в историю в волне 1 не пишется (отмечено как follow-up).
- Все новые строки — через i18n (RU+EN), советы и статусы — кодами.

## 5. Тесты

- Табличный тест Cause→Status/Advice (все значения Cause покрыты).
- RunSingle: одна цель, история не пополняется, busy соблюдается.
- MeasureSpeed: httptest-сервер с искусственным троттлингом (лимит байт/с)
  → slow; быстрый → normal; обрыв → Err. Пороговые границы табличным тестом.
- Фронт: check-i18n.mjs проходит; npm run build.

## Не в этой итерации

- Замер скорости в истории/отчёте; авто-замер в прогоне; SpeedURL для
  сервисов кроме YouTube (добавлять по мере находки стабильных URL);
  предупреждение о старой geo-базе в UI.
